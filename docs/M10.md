# M10：物理像素、4K 档位与 Intel QSV

## DPI 与显示器坐标

引擎在初始化 OBS 前启用 Windows Per-Monitor V2 DPI awareness，并用
`EnumDisplaySettingsEx(..., EDS_RAWMODE)` 取得每块显示器的物理像素尺寸和桌面位置。
`GET /api/v1/targets`、原生区域覆盖层、浏览器回退框选及 OBS crop 均使用同一物理像素坐标系。
例如 3840×2160、150% 缩放的显示器仍必须返回 `width=3840,height=2160`，而不是
2560×1440。混合 DPI 下每块显示器的 `x/y` 也按物理虚拟桌面坐标解释。

手测：Windows“高级显示”确认活动信号为 3840×2160，将缩放依次设为 125%、150%、200%，
重启引擎并请求 `/api/v1/targets`；三次尺寸必须保持 3840×2160。随后用原生 picker 选择
已知矩形，成片分辨率应与选择值一致（编码偶数对齐最多相差 1 像素）。

## 输出档位

`quality` 支持 `1080p30`、`1440p30`、`2160p30`。显示器和区域模式保持源宽高比，且输出
不会放大超过源物理尺寸：4K 来源选 2160p30 输出 3840×2160；2560×1440 来源选 2160p30
仍输出 2560×1440。窗口/游戏继续使用 OBS 捕获源的动态尺寸策略，不承诺强制放大到 4K。

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\record-regression.ps1 `
  -Quality 2160p30 -Encoder x264 -Seconds 20
```

## Intel QSV

当前 OBS 的非 deprecated H.264 ID 是 `obs_qsv11_v2`；旧 `obs_qsv11` 仍列在探测结果中，
但明确标为 deprecated/unavailable，防止把旧 ID 冒充为可用。`/api/v1/encoders` 的
`unavailable_reason` 区分模块加载失败、Intel GPU/驱动未注册以及普通硬件不支持。

`pack.ps1` 已经复制 OBS rundir `bin/64bit` 的全部 DLL；此外会从该 OBS 源树的 `.deps`
中发现并复制 `vpl/libvpl/mfx/libmfx` DLL。部分 OBS Windows 构建把 oneVPL dispatcher
链接进插件，运行时使用 Intel 显卡驱动，因此 deps 中没有额外 VPL DLL是正常情况；脚本会明确打印
“未发现可再分发 DLL”，而不会声称已经捆绑。Intel 机器必须看到 `obs_qsv11_v2.available=true`
并完成真实短录；否则以 `unavailable_reason` 和 OBS 日志为准，仍可诚实降级到 x264。

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\record-regression.ps1 `
  -Encoder qsv -RequireHw -Quality 2160p30
```
