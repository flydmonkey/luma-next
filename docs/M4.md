# M4：硬件编码探测、选择与诚实降级

状态：完成；本机 AMD AMF 与 x264 均通过 20 秒真实录制。

## 探测口径

引擎加载 `obs-x264`、`obs-ffmpeg`，并尝试加载 `obs-qsv11`、`obs-nvenc`。随后采用
OBS 前端相同的 `obs_enum_encoder_types` 口径，只认 video/H.264 且非 internal、非
deprecated 的真实注册项。DLL 存在不等于编码器可用。

`GET /api/v1/encoders` 返回候选项及 `available/hardware/vendor`。显示名与 OBS id：

- Software (x264) → `obs_x264`
- AMD HW H.264 (AMF) → `h264_texture_amf`
- NVIDIA NVENC H.264 → `jim_nvenc`；兼容实现为 `ffmpeg_nvenc`
- Intel Quick Sync H.264 → `obs_qsv11`

本机结果为 x264、AMF 可用，NVENC/QSV 不可用。设置文件增加 `encoder`，PUT 或 start
覆盖传入未探测到的 id 会返回 422。

## 降级与遥测

start 先实际创建并启动首选 encoder。创建失败、output start 失败或启动后立即停止时，
同一次请求释放半成品并尝试 `obs_x264`。session 与 stop 保留：

- `encoder_requested`
- `encoder_active`
- `encoder_fallback`
- `fallback_reason`

因此硬编失败不会被伪装成硬编成功。若 x264 也失败，start 直接返回错误；stop 仍执行
M1 的帧数、文件、双流与时长验证。

可用以下仅用于回归的环境变量稳定制造降级：

```powershell
$env:LUMA_FORCE_ENCODER_FAILURE='h264_texture_amf'
cargo run -p luma-engine
# 另一个终端选择 AMF start，session 会显示 active=obs_x264 和明确原因
```

## 双档回归

```powershell
# x264 + 可用时的首选硬编（AMD 优先）
powershell -ExecutionPolicy Bypass -File .\scripts\record-regression.ps1

# 只测 AMF；不可用时正常 SKIP
powershell -ExecutionPolicy Bypass -File .\scripts\record-regression.ps1 -Encoder amf

# AMF 不存在或发生降级均失败
powershell -ExecutionPolicy Bypass -File .\scripts\record-regression.ps1 -Encoder amf -RequireHw
```

ffprobe 的 `codec_name=h264` 不能证明由哪块硬件编码，因此脚本以 session 的实际
`encoder_active` 判断编码路径，再独立用 ffprobe 验证成片结构与时长。

M4 不承诺 4K/60、HEVC/AV1 或全厂商同级调优，也不扩大屏幕/音频采集范围。
